# Local Capability authoring

`app build` and `app dev` synchronize selected local Capability packages before
compiling Plugins. Contract identity, version, configuration, and provider choice
remain explicit. Production startup does not run generators.

## Create one contract

```sh
lenso app create my-app --runtime empty
cd my-app
lenso app contract new example.text
# Or author the contract as a Rust trait:
lenso app contract new example.search --source rust
lenso app build
```

The default creates a Descriptor/JSON Schema package under
`contracts/example.text/`, with a generated TypeScript projection. This path needs
no Cargo. Rust source creates `src/contract.rs`, a regular Cargo package, and a
Rust runtime projection; Cargo is needed during authoring. Neither requires an
App configuration file. Edit the initial `execute` Operation to match the domain.

Each Capability has one authority. For Rust packages, a small extractor compiles
only the contract source module with the package's resolved build-dependencies;
it does not first compile a consumer of stale generated code. The package's
codegen dependency generates its projections. The ordinary build script continues
to check freshness for consumers outside the App workflow.

## Existing packages

The existing Cargo metadata still works:

```toml
[package.metadata.lenso.contract]
descriptor = "capability.json"
projection = "rust-runtime"
output = "src/generated.rs"
# Optional source locator. Existing src/contract.rs is also recognized.
source = "src/contract.rs"
```

Additional projections can be declared in `projections = [{ projection =
"typescript", output = "generated/text.ts" }]`. Outputs must stay inside the
owning package. Rust source modules need the build-dependencies they normally use,
including `lenso-contract-codegen`; dependency identity and enabled features are
preserved. No arbitrary regeneration script is inferred or executed.

A Bun consumer/provider can generate its own projection from the same authority:

```json
{
  "lenso": {
    "pluginId": "example.uppercase",
    "runtime": "bun",
    "contract": {
      "descriptor": "../../contracts/text/capability.json",
      "projection": "typescript",
      "output": "generated/text.ts"
    }
  }
}
```

This is package tooling metadata, not another Contract or App manifest. The
existing Plugin identity/runtime fields and normal package dependencies remain.
Contract-only npm packages are not discovered as business Plugins.

Only App-owned `contracts/`, selected Plugin package declarations, and local Cargo
dependency closures participate. Unadopted shared Plugin candidates do not trigger
generation. Outputs, schemas and traversals are bounded; symlink outputs and
multiple output owners fail explicitly. Existing authored files cannot be
replaced by projections. Generated bytes that do not change are not rewritten,
so watching does not create a generation loop.

## Implement and consume the typed role

With `lenso-contract-codegen` 0.9 and `@lenso/bun-plugin` 0.4.1, a Bun provider can
use the generated Capability directly:

```ts
import { definePlugin } from "@lenso/bun-plugin";
import { Text, type TextProvider } from "../generated/text.ts";

export default definePlugin({
  provides: [Text],
  create(): TextProvider {
    return {
      async uppercase(_context, request) {
        return { ok: true, value: { text: request.text.toUpperCase() } };
      },
    };
  },
});
```

Bun dependencies use `dependencies: { text: Text.required() }`; `optional()` and
`many()` retain their existing cardinality semantics. The property name is the
requirement ID unless an identical explicit ID is supplied. The CLI statically
extracts these declarations and binds exact generated providers. It does not
import Plugin business code to discover contracts. The local Bun build profile
currently admits Request providers; Stream/Event providers fail explicitly.

A native consumer uses the existing qualified generated Client:

```rust
#[lenso::plugin]
#[derive(Clone, Debug)]
struct Web {
    #[dependency(id = "uppercase")]
    uppercase: text::TextClient,
}
// Inside the HTTP handler:
let response = self.uppercase.uppercase(UppercaseRequest { text: input.text }).await?;
```

Domain code no longer needs a ToolProvider tool-name string or JSON round trip.
Use ToolProvider separately when exposing behavior to an Agent. Multiple eligible
providers still require an explicit Root choice; these conveniences grant no
permissions and change no Host admission policy.

## Changes and compatibility

All contracts validate before generated outputs are installed. Failed validation
leaves the old projections and running development App intact. Source changes
while extraction runs are rejected. Source-owned snapshots are checked against
the previous committed snapshot on first generation when available, and against
the previous successful local synchronization afterward. Descriptor-first packages
use that local baseline after their first synchronization.

The `.lenso/contracts/` cache is a development comparison baseline, not a release
lock or a substitute for comparison against the last published contract. Do not
remove it to bypass a compatibility error. Versions never bump automatically.
Compatible changes require the correct authored version; a new incompatible
Capability series belongs in a new package. Existing exact-digest projections
remain usable across generator cohorts. Regenerating a legacy Guest SDK 0.4
projection requires its compatible codegen build-dependency; the bundled generator
uses Guest SDK 0.5. No silent SDK migration occurs.

Web routes/assets stay in Web Plugins; this change does not add filesystem routing
or stateful HMR. Existing custom Hosts and standalone Plugin commands remain
available. See `lenso-examples/fixtures/vnext-typed-local-app` for the runnable
Rust-source -> Rust/TS projections -> typed offline invocation proof.
